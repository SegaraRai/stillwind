# ソース同一性と診断の設計

## ソース改訂

`SourceFile` は一つの不変な原文、`FileId`、`Option<SourceUri>`、`Option<source_map_source>` と行表をまとめて保持する。`FileId` はコンパイルと診断で共有するソース改訂 ID であり、診断専用の番号ではない。`SourceRegistry` がそのスコープ内で発行する。独立したスコープの ID は重複してよく、プロセス全体のカウンタは使わない。診断の範囲は登録済みの `SourceFile` に結び付け、呼び出し側が ID と URI を別々に対応付ける API は設けない。

`SourceUri` はホストが供給する、ユーザーから参照できる文書の絶対 URI である。`file:` に限定せず、Rust 側で OS のパスとして解釈・正規化しない。診断の表示名が必要ならアダプターが URI から決める。`SourceFile` に表示名や汎用の `path` は持たせない。URI が `None` のソースは、独立した文書としてホストから参照できない内部バッファである。この場合、原文を指すソースマップ名も持てず、公開診断の位置や修正編集には使えない。エディタの未保存文書や Wasm 入力もホストが参照可能なら URI を持つ。

一つの URI に複数の改訂が存在し得る。各改訂の内容 fingerprint が公開位置の `revision` になる。生成・投影された入力に対する検出結果は、公開前に参照可能な原文改訂へ戻す。

## 用途ごとの識別情報

| 値                                    | 所有者・供給時点                          | 用途                                                            |
| ------------------------------------- | ----------------------------------------- | --------------------------------------------------------------- |
| `SourceUri`                           | ホストが原文の登録時に供給                | 診断、編集対象、改訂確認                                        |
| `source_map_source`                   | ホストが原文の登録時に供給                | 生成ソースマップへそのまま記録する名前。URI から導出しない      |
| `ModuleId`                            | ホストがスクリプトの解析前に供給          | import 解決、モジュール間参照、生成名などのコンパイル上の同一性 |
| `ScriptLanguage` / `ScriptModuleKind` | ホストがスクリプトの解析前に供給          | Oxc の構文選択。Rust は拡張子から推測しない                     |
| `CssSourceName`                       | ホストが CSS ローダーへ全文を渡す時に供給 | CSS の import・リソース解決に使う参照名                         |

これらは用途が異なる。モジュール ID、CSS 参照名、ソースマップ名から診断 URI を作らない。CSS と JS の原文は同じ `SourceFile` の契約を使い、どちらも URI がある場合は診断できる。CSS の初回ロードと JS の解析では保持するソース集合を分ける。プロジェクト内の ID 発行スコープを共有し、診断時にはアクティブな CSS スナップショットと JS レジストリの原文を参照する。CSS の前処理と上流ソースマップの扱いは別途設計する。

現在のプロジェクト入力では `ProjectSource.path` が `ModuleId` の入力欄である。この値はモジュール解決の同一性として使い、原文の URI やソースマップ名には転用しない。

## 診断と修正アクション

内部の `CompileError` / `LintFinding` は型付きの原因と `Span` を持つ。`Reporter::collect` または `LocatedDiagnostic::from_compile` / `from_lint` が、登録済みの原文に対して各 `Span` を解決する。未登録 ID、無効な範囲、URI のない原文は公開位置として拒否する。

公開診断は主範囲を一つ、関連範囲を零個以上持つ。各位置は URI、内容 fingerprint、半開 UTF-8 バイト範囲、UTF-16 オフセット、0 始まりの行と UTF-16 列を持つ。複数ファイルの原因は関連範囲で示す。CLI などのテキスト表示では行・列を 1 始まりにする。NAPI は共通層で解決した値を転送し、LSP アダプターは同じ値を LSP の range と related information に変換できる。

リントには代替となる修正アクションを零個以上付けられる。一つのアクションには一個以上の編集が必要で、複数文書にまたがれる。同一アクション内の重複編集は拒否する。適用前には全対象 URI の現行 fingerprint を照合し、一つでも異なればアクション全体を拒否する。

`Reporter` は一回の解析または更新のために作る。ソース ID を発行せず、位置と編集を検証し、リントの抑制と `off` / `warn` / `deny` を適用する。同じバッチに同一 URI の異なる改訂を混在させない。`finish` は解決済みの `DiagnosticBatch` を返す。

## 更新時の状態

`ProjectSession` はアクティブな成果物と最後に報告したモジュールごとの診断バッチを保持する。watch 中に CSS の再ロードが失敗した場合は直前の成果物を保持し、失敗した試行の診断を報告する。成功した更新では対応する成果物と診断を更新する。報告済み位置は解決済みなので、古い原文の行表を診断表示のためだけに保持する必要はない。
