`style(...inputs)` returns props for one element. The compiler generates the CSS
for its utilities at build time. React receives `className` and `style`; the
other frameworks receive `class` and `style`. Spread the result onto the element.

## Inputs

| Input                       | Example                              | Effect                                              |
| --------------------------- | ------------------------------------ | --------------------------------------------------- |
| A utility string            | `"rounded-md p-4 hover:bg-blue-700"` | Adds the utilities                                  |
| An array                    | `["p-4", "text-sm"]`                 | Adds each item                                      |
| A condition                 | `active && "bg-blue-500"`            | Adds the item when the condition is true at runtime |
| A ternary                   | `dark ? "bg-black" : "bg-white"`     | Adds one of the two items                           |
| An object with variant keys | `{ "hover:": "underline" }`          | Adds the value under the variant                    |
| A custom property           | `{ "--progress": value }`            | Sets the property in the inline style               |
| A `class` field             | `{ class: className }`               | Adds classes from other stylesheets without CSS     |
| A stored `style()` result   | `base`                               | Adds the classes of the base                        |

`false`, `null`, and `undefined` add nothing. Ref, keyframes, and view transition
calls are also inputs; see [`style.ref()`](/docs/macros/ref),
[`style.keyframes()`](/docs/macros/keyframes), and
[`style.viewTransition()`](/docs/macros/view-transition).

Write utility names as literals. The compiler reads them from the source, so a
name that your code builds at runtime produces no CSS.

Inside an object with variant keys, write utilities only. A `class` field, a
custom property, a ref, or a stored `style()` result belongs outside that object.
[invalid-rule-group-input](/docs/lints/invalid-rule-group-input) reports these
inputs.

## Static input

A call with only static input compiles to a plain object. The compiler decides
the order of the CSS rules, so no runtime library merges classes.

<CompiledExample>

```tsx
import { style } from "stillwind/react";

export const props = style("rounded-md p-4 text-blue-600");
```

</CompiledExample>

## Conditions and custom properties

Variants such as `hover:` stay in CSS. A JavaScript condition only chooses which
compiled class the element gets. A custom property becomes part of the inline
style.

<CompiledExample>

```tsx
import { style } from "stillwind/react";

declare const active: boolean;
export const props = style("p-4", active && "bg-blue-500", {
  "--progress": 0.5,
});
```

</CompiledExample>

The compiled code imports `stillwindClsx` to join class names. In development,
Stillwind imports a checked version that reports invalid values.

## Base styles

A stored `style()` result passed to another call is a base. The compiler places
the base's CSS before the CSS generated by the call that receives it. The later
declarations win when the other cascade criteria, such as specificity and
importance, are equal. See [CSS ordering](/docs/concepts/css-ordering).

<CompiledExample>

```tsx
import { style } from "stillwind/react";

const base = style("rounded-md p-2");
export const props = style(base, "p-4 bg-blue-600 text-white");
```

</CompiledExample>

A base can come from any framework entrypoint and passes on its classes only.
The receiving call returns its own framework's props. The base's inline style and
custom properties do not carry over, and [invalid-style-composition](/docs/lints/invalid-style-composition)
reports them. Set them in the call that receives the base.

Store a base in a variable before you pass it. A `style()` call written
directly inside another call produces no CSS, and
[invalid-style-input](/docs/lints/invalid-style-input) reports it.

## Argument order

For utilities and bases, the position of an argument does not decide which
declaration wins. A later argument does not override an earlier one:

| Arguments                                                          | Which CSS comes later                                                                                            |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| Utilities without a condition, in strings, arrays, or variant keys | The stylesheet's order of utility definitions decides. The order in the call and in each string does not.        |
| A base and the utilities of the call                               | The utilities of the call. `style("p-4", base)` and `style(base, "p-4")` produce the same CSS.                   |
| Two bases                                                          | The base that is built on the other one. When neither is built on the other, the argument order does not decide. |
| Items with a condition                                             | They come after the items without a condition, in the order in which you write them.                             |

These calls produce the same CSS, and `p-4` wins in both:

```tsx
style("p-2", "p-4");
style("p-4", "p-2");
```

Custom properties in the inline style follow argument order. When two
arguments set the same custom property, the later one wins.

Do not reorder arguments to fix a conflict. Reordering does not change the
result, and it does not remove a finding of
[conflicting-utilities](/docs/lints/conflicting-utilities),
[ambiguous-style-base-order](/docs/lints/ambiguous-style-base-order), or
[interfering-imported-style-base](/docs/lints/interfering-imported-style-base).
Remove the utility that should not apply, or build the overriding style on the
other style. [CSS ordering](/docs/concepts/css-ordering) describes the complete
rules.

## How props combine at runtime

When the compiler cannot reduce a call to a plain object, a runtime helper
combines the inputs:

- Classes keep their order.
- A later inline style replaces an earlier one.
- A later custom property replaces an earlier one with the same name.
- Custom properties apply on top of an inline style.

## Forward props to a component's element

`style.forward()` passes the class and style props that a component receives to
the `style()` call of its element. Write it as one argument of the call:

```tsx
import { style } from "stillwind/react";

export function Card({ className, style: inline, ...props }: CardProps) {
  return <div {...props} {...style("rounded p-4", style.forward({ className, style: inline }))} />;
}
```

The forwarded props apply after every other argument:

- Forwarded classes come after the component's own classes.
- Forwarded custom properties and inline style declarations replace the
  component's ones with the same name.
- An inline style object is merged with an object, and a string is joined with
  a string. When one is a string and the other is an object, Vue receives
  both in an array. The other frameworks receive one string.

`style.forward()` reads the `class`, `className`, and `style` keys, so pass the
props under the names that your framework uses. When both class keys are
present, it joins them. Class values accept strings, arrays, and objects, as in
`style()`. Inline style strings are not parsed into objects.

You can also pass all props, as in `style.forward(props)`. In that form, make
sure that no prop that comes after the result replaces its `className` or
`style`:

```tsx
// Wrong: props.className replaces the merged class.
<div {...style("p-4", style.forward(props))} {...props} />
```

`style.forward()` cannot be inside a variant object. A
[`style.recipe()`](/docs/macros/recipe) factory takes it as its second argument. The
Lit, Alpine, and vanilla entrypoints do not provide `style.forward()`.

A call can have several `style.forward()` arguments. Their inline styles and
custom properties apply in argument order, so a later value replaces an earlier
one. Their classes are joined, and as with several bases, the CSS order decides
which class wins, not the argument order.
[multiple-style-forwards](/docs/lints/multiple-style-forwards) reports such
calls.

When a module passes a `style()` result to an imported component, the CSS of
the component's module comes first, so the caller's utilities win. See
[CSS ordering](/docs/concepts/css-ordering#files-that-pass-styles-to-components).

## Side effects in arguments

The compiler can evaluate arguments in any order, and it can skip arguments
whose result is not used. Arguments must not perform I/O, change shared state,
or depend on how often they run. Calculate such values before the call.
[mutating-macro-argument](/docs/lints/mutating-macro-argument) and
[suspending-macro-argument](/docs/lints/suspending-macro-argument) report the
cases that the CLI can detect.

[Reusable styles](/docs/guides/reusable-styles) for task-based guides.
